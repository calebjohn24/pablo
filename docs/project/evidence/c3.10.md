# C3.10 acceptance — ordered model profiles and routes

F01 now resolves named models and ordered routes through actual Rust deployment resolution and CLI validate/explain/render. A single-entry route performs the existing model/tool/model task through CLI and ACP. Multi-entry fallback and distinct per-attempt deadlines remain explicitly owned by C3.11 and reject before credentials or runtime effects. [The frozen contract](../contracts/c3-model-routes.md) defines the complete policy and compatibility boundary.

Schema v1 advances to revision `c3.10`. Composed profiles require exact model/provider/credential identity, with provider-specific endpoint/auth rules. Route references expand in declared order with bounded depth/entry count, no duplicate references or resolved entries, and no cycles. Every potentially eligible entry satisfies capability, root-token and host destination/credential/model ceilings. Private keys are neither resolved nor hashed during inspection. Gateway upstream routing is labeled separately as opaque to Pablo.

## Executed F01

- Six Rust integration tests verify three-provider nested-route order; exact endpoint/model/credential/protocol/options; derived-default provenance; render/reload identity; missing, duplicate and cyclic references; unsupported requirements and auth consumers; retry-owner/attempt constraints; all-entry authority; selected credential lookup; token clamping; typed override recomputation and exact inherited subsequences. Thirteen invalid-configuration variations fail without partial selection.
- The immutable subsequence API accepts only existing entry names in existing order. Reorder, repetition, replacement, empty routes and added destinations reject; attempt capacity narrows to the retained list. No child runtime is introduced at this checkpoint.
- The CLI fixture validates its actual explanation against both checked-in schemas, verifies three ordered identities and reloads rendered TOML with identical effective fingerprint/route. Missing real credentials do not prevent offline inspection; synthetic invalid ambient credentials never appear in its output.
- Multi-entry `run` and ACP startup reject with C3.11 ownership even when a local fixture endpoint is supplied; the receiver observes zero requests. Separately shortened per-attempt deadlines also remain unavailable until C3.11 rather than being silently ignored.
- Single-entry OpenRouter performs four actual tasks/eight fixture requests: configured CLI, equivalent legacy CLI and two fresh ACP sessions in a reused process. Every task reads a real Unicode evidence file, sends its exact result to the second model call and returns the expected answer/accounting. Configured and legacy request bodies are identical. Legacy `--model`/`--provider` flags with a selected route reject before requests instead of being ignored.
- Typed per-task overrides refresh derived endpoint/root-token/attempt defaults; explicit model IDs and profile token caps remain operator-authored. A profile cap cannot increase the root allowance. The existing GLM defaults and unlimited filesystem-work defaults remain intact.

The user-facing examples are [three-provider inspection](../fixtures/c3-model-routes/three-providers.toml) and [single-entry execution](../fixtures/c3-model-routes/single-openrouter.toml). The former validates using the release executable with an explicit workspace binding. Examples contain only credential references; live use requires the operator's private key and a real endpoint/model for the Open Responses placeholder. The offline F01 checks made no paid calls. A subsequent user-requested [credential retest](c3.10-openrouter-key-retest.md) passed through the current release CLI and ACP.
