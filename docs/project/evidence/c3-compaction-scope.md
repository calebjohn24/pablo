# C3 basic compaction scope review

On 2026-09-10 the user explicitly requested basic compaction in the C3 release, taking inspiration from Codex. The existing design brief already requires bounded-run compaction in section 23 and a single overflow recovery in section 28.8; C3's previous checkpoint map omitted an owner. This change adds **C3.12a**, after fallback failure/accounting acceptance and before output validation, without renumbering existing checkpoints or rewriting history. C3.13 depends on C3.12a; the combined extensibility and deployment-preset gates now exercise compaction too. CP01/CP02 define the observable acceptance. The product context is unchanged, so its reviewed hash remains unchanged.

The implementation scope is one bounded summary pass per task, triggered near a declared context threshold or by a recognized overflow rejection, followed by at most one overflow recovery attempt. Preserve the instruction/tool prefix, original task and constraints, recent complete tool-call/result pairs, retained private continuation and real completed effects. Commit a smaller replacement history only after valid summary completion. Summary work, fallback attempts and recovery use the same root budgets; summary text remains derived task data. Expose compaction identity/size/trigger and a policy-controlled summary. Exact configuration defaults and protocol/error mappings must be frozen at C3.12a before code changes.

Inspiration was checked against the available local Codex checkout at commit `37485ada86664836ef45f205956a31f822a22a00`: `codex-rs/core/src/codex/compact.rs`, `codex-rs/core/templates/compact/prompt.md`, and the referenced history bridge. That snapshot requests a concise handoff, retains user context, and replaces history after summary completion. This is an implementation reference, not a claim that the checkout matches today's released Codex. Pablo will reuse the pattern within its own one-task lifecycle, cancellation, budgets and privacy rules; no Codex source or prompt was copied.

The current [official OpenAI compaction guide](https://developers.openai.com/api/docs/guides/compaction) separately describes carrying a reduced context forward and preserving its returned state. Its standalone API returns opaque encrypted state and expects input that still fits the model window. That API is not selected for Pablo: C3 keeps provider-neutral summary generation and the user's Vercel/OpenRouter GLM defaults. No OpenAI model/key, durable session store, persistent memory, retrieval system, tokenizer bundle or recursive summary hierarchy is required.

This review changes release planning only. Compaction remains pending and is not advertised as implemented. Project consistency, helper tests, dependency/fixture ownership review and whitespace checks are recorded with the accompanying C3.11 handoff.
