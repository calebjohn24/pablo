# C3.9 acceptance — native Open Responses

C3.9 implements OR02 and the pinned [OR01 contract](../contracts/c3-open-responses.md) through the default Rust core, CLI and ACP executable. Explicit deployments select `open_responses`, a complete HTTPS endpoint, endpoint-specific model, `open-responses-text-tools-v1` and an exact scoped credential reference. Configuration schema v1 advances to revision `c3.9`; inspection, render, provenance and frozen fingerprints follow that revision. Vercel/OpenRouter GLM defaults and unlimited filesystem-work defaults remain unchanged.

## Executed acceptance

| Requirement | Evidence |
| --- | --- |
| Core, CLI, ACP and real continuation | OR02 runs eight tasks and 24 actual fixture HTTP requests: CLI, direct Rust measurement host and two independent ACP sessions in a reused process, with content capture both off and on. Each task performs two actual `fs.read` calls against fresh Unicode evidence. Every subsequent request preserves stable instructions/tools and the complete ordered prior output plus actual correlated result. The final answer derives from the files, not copied request arguments. |
| Text, items and private reasoning | Seven-byte HTTP writes exercise UTF-8/SSE boundaries; pinned CRLF wires also pass byte-by-byte parser tests. Multiple content parts, assistant phases, argument fragments, opaque reasoning and summaries survive the two tool rounds. Native model identity exposes endpoint/profile/revision and requested/resolved model. Only supported items enter the typed private carrier; raw reasoning that cannot round-trip rejects. Debug, native traces even with capture, CLI/ACP output, diagnostics and actual OTLP Protobuf omit private continuation and credential sentinels. |
| Accounting and terminal behavior | Each full task settles 450 input, 90 output and 240 cache-read tokens, with unknown cache-write/cost. Paired CLI/ACP cases preserve null, explicit zero and raw `9007199254740993` exactly in decimal-string task accounting. Truncated function JSON in a max-output incomplete response produces the output-token limit and executes no tool. Completed outcome usage retains the existing numeric projection; JavaScript clients use task accounting for exact large counters. A repeated DONE after logical EOF cannot produce a second terminal or duplicate usage. |
| Closed failure and bounds | Thirty paired CLI/ACP cases cover rejection/redirect without follow, missing/mismatched named events, duplicate sequence, changed/missing item/response identities, wrong snapshots, missing fields/terminal/DONE, duplicate terminal/JSON fields, malformed JSON/UTF-8, unknown semantics, raw reasoning, image/refusal content, invalid token counts/totals, excessive JSON containers, a frame above 32 MiB and body disconnection. Each produces one expected closed failure with response-received certainty and no tool dispatch/retry/private diagnostic. Core tests narrow retained continuation to 32 bytes and prove rejection; shared transport bounds remain tested. |
| Cancellation and reuse | CLI SIGINT and ACP cancellation close the peer-observed socket both before the first tool and after a completed file read. The interrupted call leaves usage unknown; completed-call usage remains in native records. One terminal is emitted, and the reused ACP process completes a subsequent fresh task with no inherited continuation. |
| Credential/header scope | Rust verifies exact consumer/destination exposure, redacted Debug/render, profile admission and derived auth-default provenance. Actual fixture requests use only the synthetic token, including `X-Api-Key`/raw. Missing, empty and whitespace credentials reject CLI/ACP startup with no trace/network effects and no Vercel/OpenRouter fallback. Application auth suffixes exclude routing/tracing/proxy headers; the header value is marked sensitive. Complete HTTPS URL, explicit model/profile and a minimum 16-token output allowance are validated before effects. |
| Compatibility and configuration | All existing Node integration suites pass, including Vercel/OpenRouter, deployment, ACP, telemetry, shell, filesystem and task envelopes. The runnable Open Responses sample passes release `config validate` offline. The ACP metadata schema now describes optional safe profile and existing deployment identities. Configuration fingerprints migrate explicitly without changing prior effective options. |

The adapter uses the shared direct HTTP/SSE transport, without new Cargo/Node dependencies, hidden retry, proxy inheritance or redirects. Continuation is task-owned, non-serializable and scoped by endpoint/requested/resolved model/revision/profile. Root context includes its logical serialized bytes without charging the public assistant projection twice. JSON work additionally rejects containers above 4,096 entries and frames above 65,536 values, alongside depth, byte, item and call limits. These are protocol bounds, not filesystem-work quotas.

Unsupported capabilities remain explicit: non-text modalities, hosted tools, provider extensions, unrepresentable raw reasoning, structured-output enforcement, background/WebSocket/compaction and server-persisted continuation. Cost/cache-write reports and hard accounting ceilings are not attested. Capability configuration is an operator declaration, not a paid-service compatibility claim. OR02 is entirely offline. The separately requested [OpenRouter key retest](c3.9-openrouter-key-retest.md) used the prior verified release and is not evidence for this new adapter.

## Matched performance

[Sanitized distributions](c3.9-measurements.json) retain binary/source/harness identity, methods and aggregate percentiles. Native macOS arm64, Node 24.11.0, Rust 1.98.1; each variant has 30 samples after five warmups, measured sequentially after tests/builds. Baseline binaries were frozen before implementation and match the C3.6–C3.8 release. The baseline source fingerprint is its recorded build-source identity; the current harness is shared across variants. Raw samples stay ignored.

Release size is **11,297,872 bytes**, up **66,736 bytes (0.59%)** from 11,231,136. New executable SHA-256: `51e2d44431e8de8f6386c4c2868432b1bcdb9ebc14b9bc57fa1f6dc4897c0bea`. Current source fingerprint: `738afcc9ee166dbe722533b3d2e8d89b6b3c7c3202d0d719fb6309e741d544ab`.

The listing increase warranted two more matched filesystem pairs, alternating current/baseline order. Listing p50 was baseline/current **1.033/1.204 ms** and **1.174/1.519 ms**; replacement **0.499/0.631 ms** and **0.522/0.616 ms**. This is a repeatable timing increase on this host, not evidence of unchanged performance. Its cause is not isolated; retain it for C3.39 release comparison. No filesystem implementation or default quota changed. The checkpoint requires measured comparisons, with no invented pass/fail latency ceiling.

## Handoff

C3.9 is complete. Merge the verified implementation and records, then select C3.10 to freeze ordered model profiles/routes and their configuration/continuation authority before C3.11 fallback execution. Keep gateway defaults and unlimited filesystem work. Later routes must reject incompatible opaque continuation rather than silently discard it. C3.39 must revisit the retained filesystem timing increase as part of the required matched release measurements.
