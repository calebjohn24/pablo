# C1.2 evidence: bounded shell loop

Date: 2026-09-05 UTC. Platform: macOS 26.6.2, Darwin arm64. Rust/Cargo 1.98.1. The source brief remains unchanged.

## Result

The existing Rust runtime now drives sequential model/tool turns. An explicit shell catalog advertises a compiled Draft 2020-12 schema, accepts bounded fragmented tool arguments, executes a real shell command, and supplies its actual result to the next model request. Instructions and tool definitions remain stable across steps. The runtime supports typed cancellation, policy denial, tool limits, and process-group cleanup through the same native/OTel lifecycle.

The decisive fixture creates a temporary evidence file. Its first model response requests a fragmented `shell.run` call. Its second model request asserts the actual shell output, stable prefix, catalog, message history, and correlated call IDs, then returns that output as the final response. The test checks aggregate usage and exactly one terminal outcome, plus run/model/tool span parentage and exact tool lifecycle timestamps against native JSONL.

Implementation contracts and current limits are recorded in [runtime documentation](../../runtime.md) and [shell documentation](../../shell.md).

## Behavior demonstrated

- Actual evidence-file round trip and two tool calls executing in order.
- Separate stdout/stderr and nonzero exit returned to the next model; only the failing tool span is marked erroneous when the model handles the result.
- Required fields, unknown fields, invalid types/limits, NUL rejection, disabled tools, environment denial, and cwd/symlink policy before process creation.
- Fragmented argument assembly, malformed JSON/call ordering, unique call IDs, model/tool/input/context limits, and stable request prefixes.
- Raw output bounds, complete serialized-result bounds under JSON escaping, truncation metadata, and explicit lossy UTF-8 output metadata.
- Cancellation before admission, at process start, at tool completion, and during provider opening/streaming.
- Cancellation and timeout cleanup of descendants, including TERM-ignoring children and background children with closed output pipes.
- Cleanup after normal leader exit, reaped shell leaders, and disappearance of owned groups before successful tool settlement.
- Event delivery failure after spawn still triggering cleanup; reserved terminal capacity across repeated model/tool transitions, including event budgets from four through ten.
- Native shell content opt-in and metadata-only OTel spans; no shell command/output copied to OTel.
- HTTP and local-file schema references rejected without retrieval.

## Findings resolved

The first integrated shell suite failed four fast-exit cases because macOS returned EPERM when signaling a group containing only exited members. The cleanup path now treats that result provisionally, reaps the leader, drains pipes, and verifies group disappearance within the cleanup deadline. A live inaccessible member cannot become a successful cleanup result. Only signal-zero probes occur after leader reaping, avoiding real signals to a recycled numeric group ID.

Review also found that a new operation could consume a closing event after a previous operation had exhausted the remaining slots. Admission now checks room for a new operation before creating its lifecycle; a test sweeps small event budgets across model/tool/model transitions. Intermediate compile errors from the extended contracts and two test-style Clippy findings were resolved before the passing gates above.

## Scope and handoff

C1.2 is complete on the current macOS host. The user's root `.env` was not read or modified, and shell fixtures ran only in temporary workspaces. No live gateway, ACP, Collector, or Linux execution was claimed.

Process groups provide owned cleanup, not containment of commands that deliberately escape their group. Hosts supply isolation and orphan reaping. Cleanup has a two-second allowance beyond the execution deadline. Explicit cancellation must be followed by awaiting settlement; dropping a run future cannot await cleanup or promise terminal delivery. Inline sinks must return promptly. Shell output is returned at tool completion in this slice; interactive handles and live shell byte streams are not implemented.
