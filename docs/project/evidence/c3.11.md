# C3.11 acceptance — ordered model fallback execution

F02 now executes ordered routes within one runtime task through core, CLI and ACP. An eligible failed attempt advances one entry, the selected entry remains sticky for later operations, and completed tools/history are retained. Every attempt has its own model/provider/span identity and shares root call/time/accounting budgets. [The route contract](../contracts/c3-model-routes.md) documents implemented behavior and the C3.12 failure-ledger boundary.

## Executed behavior

- Five Rust integration tests cover first proven-unsent failure → second success with no third dispatch, selection retained across a real filesystem tool, and fallback after completed tool history. Requests preserve the actual history and independently clamp profile token bounds; a primary bound of 64 does not narrow the next profile's 128. Three model attempts have distinct span IDs and one run/trace identity, with exactly one tool call.
- Each eligible entry's accounting bounds are validated before dispatch. An unattested final entry rejects the whole route before any provider call. A root model-call limit of one permits the first failed request and prevents the next dispatch. Per-entry ledgers settle into the same root accounting totals.
- Proven-unsent failure plus two successful calls settles charged tokens/cost to 10/4 with three model calls. Received transient or explicitly opted-in uncertain failure plus one success retains 15 tokens/10 micro-USD of conservative charges; unknown actual usage/cost remains unknown. These are synthetic attested bounds, not claims about live gateway spending guarantees.
- Default uncertain delivery, escaped text, cancellation and an exhausted route-attempt allowance stop fallback. A 10 ms attempt deadline cancels an owned five-second fixture future promptly; default behavior reports `model_attempt_timed_out`, while explicit uncertain-transport opt-in can advance and retains the failed attempt's reservation. Root expiry/cancellation retain their existing outcomes.
- Four Node F02 tests exercise actual HTTP/SSE and executable behavior. CLI and two fresh ACP sessions in each of two scenarios prove initial HTTP 503 → sticky second entry, and HTTP 503 after a completed file read → second entry with identical accepted history. Each successful task returns exact fresh Unicode evidence with three model calls and one tool call. No third entry receives a request. Native attempt spans, run identity, terminal accounting and private error-body redaction are checked.
- Open Responses private history cannot cross to a chat gateway; chat assistant history cannot enter the current Open Responses adapter without its required private projection. Both transitions stop with `continuation_incompatible` before contacting the next entry, retaining the completed file read and the two attempts already made.
- Host resources resolve all route credentials through their exact scoped references before effects. ACP may reuse immutable adapters only when deployment, bindings and private credential values match; selection/history remain task-local. Ordinary F01 tests continue to verify private credential rejection, schema-valid explanation, render/reload identity and single-entry CLI/ACP equivalence.

Schema v1 advances to `c3.11`, enabling validated routes and distinct attempt deadlines. The production golden retains identical effective config, sources and provenance; only revision and identity values migrate. Its effective fingerprint is `sha256:032d4bd96a06de830ee5dc5e743cf69211ddd2975dd14b9e37a71c9c28a6fdb9`. The root RunSpec retains its root token bound, and each selected attempt applies its own narrower bound. GLM provider defaults and unlimited filesystem-work defaults remain unchanged. No live provider call was made for this checkpoint.

## Performance

[Sanitized reports](c3.11-measurements.json) retain seven lifecycle and two filesystem variants plus four alternating lifecycle and two reversed-order filesystem follow-ups. Each uses 30 measured samples after five warmups on native macOS arm64, Node 24.11.0 and Rust 1.98.1. Builds/tests finished before measurements; runs were sequential. Ordinary interactive source/document review occurred during follow-ups, so this is not a claim of a controlled idle host. Failed/partial preliminary series are excluded. Raw sample arrays remain ignored.
