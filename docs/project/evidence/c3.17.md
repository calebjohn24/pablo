# C3.17 — MCP Streamable HTTP

M03 enables Streamable HTTP through the async Rust MCP factory using the same
normalized session, bounded catalog, schema validation and registry as stdio.
CLI/ACP MCP and Collector acceptance remain C3.18. No live provider, external
server, credential-file inspection or stream-resumption claim is made here.

## Implementation and acceptance

- The official pinned Rust SDK (`rmcp=3.3.0`, protocol `2025-11-25`) retains
  initialization/correlation. A bounded HTTP transport owns POST response readers;
  it accepts JSON and SSE without SDK retry/cache/multi-round call helpers.
- Independent Python SDK `mcp==2.2.0` supplies a separate stateful HTTP server for
  both JSON and SSE. Each mode initializes, discovers and reads a freshly created
  synthetic file. Recorded requests prove distinct correlated IDs, negotiated
  version/session headers and one DELETE at close, with no GET or invocation replay.
- GET streams are optional and unused in this tool-only cut. Bounded SSE priming,
  comments, CR/LF and data frames are supported. Partial streams, wrong response
  IDs, unsafe redirects, changed/oversized sessions and frame/progress overflow
  fail explicitly. Limits are 2 MiB per frame, 4 MiB per POST stream and the existing
  shared progress/catalog/result limits. One bounded response queue and per-server
  request serialization avoid accumulating pending streams.
- Host configuration requires HTTPS. Scoped `mcp.headers` credentials bind the
  exact server definition and header name; values are marked sensitive. Public
  unscoped credential access rejects. Redirects, retries and proxies are disabled.
  Literal loopback HTTP exists only as a crate-private synthetic fixture override.
- Cancellation sends an explicit bounded notification directly to the same
  endpoint: the SDK sender can still be occupied by the interrupted POST. A fault
  peer proves cancellation reaches the wire with the original request ID, including
  after a disconnect. The notification shares the original cleanup allowance.
- Cleanup interrupts HTTP I/O, joins the SDK, drops response readers and attempts
  bounded session DELETE. Already expired sessions (404) and unsupported DELETE
  (405) are handled explicitly. A failed request is never transparently reinitialized
  or replayed; a caller must begin a fresh admitted run.
- A dispatched call without a correlated response retains remote-completion
  uncertainty after cancellation/DELETE. Shared tool results and metadata expose
  this flag; old serialized MCP results default it to false. Correlated responses
  clear uncertainty. Remote effects are never claimed rolled back. Session tokens,
  credentials and raw peer errors stay out of metadata-only telemetry.
- `mcp::session` now owns shared discovery/call/result logic; `mcp::stdio` retains
  compatibility names. The existing stdio independent and runtime tests still pass,
  including actual model-result consumption and cleanup before terminal delivery.

## Verification

- `cargo test --workspace --locked`: 222 passed. Final core rerun: 44 passed.
- Explicit independent suite (`mcp:: -- --ignored --skip measure_http`): 5 passed;
  explicit stdio runtime integration suite: 2 passed. HTTP coverage includes both
  independent formats plus ten fault modes: redirect, session bound, disconnect,
  frame bound, progress bound, wrong ID, changed/expired session, hanging call and
  unsupported DELETE. Parser and credential-scope unit checks run in the ordinary
  suite. The separately ignored performance test is not counted as acceptance.
- Final interface suite: 250 passed. Project tests: 34 passed. TypeScript,
  warnings-denied Clippy, formatting, schema/golden audit and debug/release builds
  passed. Release tests are compiled separately before performance measurements.
- Initial failures came from the new credential fixture missing mandatory workspace
  and gateway declarations, and an obsolete expectation that HTTP admission remain
  unsupported. These were corrected. One full interface run reproduced C3.15's
  F03 notification count of three rather than four; the focused 18-test rerun and
  subsequent full suite passed without a fallback change. C3.33 retains that
  unresolved cross-checkpoint ordering investigation.
- Root credentials and raw runtime data remained private. All network traffic was
  local synthetic traffic. TLS/remote deployment and Collector/ACP MCP claims are
  outside this evidence.

## Performance

[Five retained reports](c3.17-measurements.json) use sequential 30-sample runs and
five warm-ups, without test/build overlap. The current measured source is
`432bfeac0864cf88ac8e18a722f7dc1f75eb0d16796f2b9fb84fb98e20f61eda`;
the saved C3.16 baseline is
`d0b9f91b2fef1fed2f2a9f3322dec27408e6065d8195b1106dac64a518e34f80`.

Baseline/current p50 ms: core 13.688/14.246, ACP initialization 10.959/10.936,
fresh prompt 16.459/16.521, warm prompt 14.706/14.611. Warm p95 is 15.791/15.541;
fresh p95 is 20.579/17.796. Filesystem prompt medians are mixed: read 1.548/1.650,
list 2.199/2.122, search 2.942/2.848, replacement 2.250/2.212, edit 1.331/1.270.
These observations do not isolate overhead or establish universal equivalence;
existing C3.39 investigations remain open. Release executable size is 11,950,320
versus 11,933,600 bytes (+16,720; 0.14%).

The native release measurement creates a fresh client/session/catalog per sample,
with one independent Python process per format. JSON startup/call/close medians
are 1.554/0.536/0.202 ms; p95 is 1.935/0.621/0.231. SSE medians are
2.222/1.032/0.527 ms; p95 is 2.550/1.178/0.643. Startup includes initialization
and discovery; close includes SDK join and DELETE. Server construction is excluded.
These are local HTTP protocol timings, excluding TLS and live model latency.
The native report records the optimized-build flag and release test-binary hash.
