# C3.22 follow-up — Native cancellation drain

Cancellation previously closed both the child dispatcher transport and root update
channel before native forwarding finished. The initial shared-consumer regression
confirmed that root completion could lose the child's terminal even though its
snapshot retained the original receipt. Cancellation now signals owned work while
keeping the native stream open. The manager closes root updates after active
execution and its acknowledged closing events settle; root settlement follows.

Native delivery observes the admitted execution cancellation token separately
from transport closure. Once cancelled, an outstanding delivery/acknowledgement
has a 250 ms window. Failure then closes producer transport and joins cleanup.
Waiting for owned cleanup to produce its next record has no such delivery timer.
The existing 30-second ordinary delivery timeout remains. Receiver loss still
forces immediate transport closure, and every path awaits owned worker shutdown.

The supervisor keeps polling the prompt while forwarding into a full root queue,
including after stop/deadline. This lets the cancellation receipt timer and joined
completion progress instead of hanging behind a blocked send. Cancellation is
latched so its ready token/deadline does not spin or discard the pending record.
No terminal is reconstructed, replayed or charged twice.

The real root/child ownership test now drains through TreeSink and verifies child
run/model closings and one Cancelled terminal before the root terminal, contiguous
native/root sequences, aggregate accounting and successful normal root outcome.
New regressions cover healthy explicit stop and deadline delivery before child
settlement; stalled receipt timeout versus slower cleanup; and nine real children
stopped with no consumer, filling the eight-slot root queue and proving the ninth
still joins with released active/queued capacity. Existing lost-receiver and
abandoned-close-caller tests remain applicable. One older provider-closure check
was aligned with the existing EOF-or-TCP-reset helper after it reproduced reset;
other socket outcomes still fail.
