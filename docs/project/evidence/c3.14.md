# C3.14 — One bounded output repair

J02 adds opt-in repair of an invalid final JSON answer within the same admitted
run. [The contract](../contracts/c3-output-repair.md) was selected before
implementation and defines settings, limits, feedback, status transitions and
capability negotiation. It extends J01 without enabling repair by default.

## Behavior and boundaries

- `output.repair.enabled=false` and `max_feedback_bytes=4096` are explicit defaults;
  feedback bounds are 512–4096 UTF-8 bytes and enabled repair requires a schema.
  Locked deployments only permit disabling/narrowing authorized overrides. The
  new tests also found and fixed missing schema/work entries in the declared
  override allowlist, completing J01's existing narrow/exact-value policy.
- Append the invalid assistant candidate, its private continuation and bounded
  code/path feedback to the existing history. Keep instructions, schema, original
  task, tool definitions, completed tool/result pairs and effects unchanged.
- Permit one correction on the selected model. Disable fallback and compaction
  during repair and reject a tool-call start as `malformed_stream` before dispatch.
  A second invalid result fails with `output_validation_failed`.
- Both final candidates share output-byte and validation-work allowances; repair
  uses the original model-call/token/cost ledger, context/event/trace capacities,
  deadline and cancellation. Preflight exhaustion dispatches no repair request.
  Uncertain interrupted delivery retains its existing accounting reservation.
- Streamed candidates are provisional. Machine CLI JSON and terminal ACP output
  contain only the validated correction on success. Plain text can include both
  streamed candidates; concatenating it does not establish valid structured output.
- `output-repair-v1` metadata carries bounded phase/counts/feedback-size only.
  Repair-enabled task revision is `c3.14`; the new ACP repair capability requires
  existing output/task/base capabilities. Output-only, legacy-task and generic
  projections retain their respective contracts. OTel marks model purpose and
  validation attempt without recording paths, feedback or model content.

  again after tightening exact typed-outcome assertions. Coverage includes
  invalid→valid, invalid→invalid, first-pass success, disabled repair, exact history
  and shared accounting, model/token/cost/output/work/context/event exhaustion,
  sink failure, cancellation/deadline during repair, provider rejection and a

  all three adapters through CLI JSON and four ACP negotiation modes. They assert

  provider failure without fallback despite a configured second route entry.

  golden audit passed. Golden changes are repair defaults/provenance, revision and

  inspection occurred in this checkpoint.

## Performance

[Measurement summaries](c3.14-measurements.json) retain sequential 30-sample runs
with five warm-ups. C3.13 release binaries are the matched baseline. Ordinary and
schema-only comparisons use the same current harness; structured CLI paths use
machine JSON so the harness checks terminal validity rather than concatenated
provisional candidates. Repair workloads assert three model calls, one actual
shell command, one invalid candidate and one validated correction, including warm
ACP sessions. Filesystem comparisons preserve existing real read/list/search/write/
edit workloads. No builds or tests overlap the measurements.

Eleven reports retain both initial comparisons, all repair adapters, the filesystem
pair and a reverse-order schema comparison.

Ordinary medians remain close. Schema warm medians converge in the reverse pair,
but the warm p95 increase repeats (16.65/15.45 ms current versus 9.52/9.11 baseline).
First-text p95 rises too, so the delay is already present before final validation;
these runs do not isolate its cause. This remains an explicit C3.39 investigation,
not a claim of performance equivalence. Filesystem prompt p50 baseline/current
(ms): read 1.653/1.623, list 2.154/2.367, search 3.063/2.928, replace 2.340/2.499,
edit 1.344/1.300. Preserve these mixed observations in release comparisons.

Binary size: 11,581,680 bytes versus 11,565,056 (+16,624; 0.14%). Current measured
source: `42bfe11f8125dcb92faabedf2ff7e763268661e25723b01a1fb1cf227f5beeb0`.

The first harness attempt stopped during warm-up because its plain-text assertion
ignored provisional streaming. Switching structured CLI measurement to `--json`
fixed that expectation; no partial report or failed measurement is counted as a
passing sample. Raw samples stay ignored local data. Timing differences are local
workload observations, not isolated repair latency or remote-provider guarantees.
C3.39 retains broader release performance acceptance.
